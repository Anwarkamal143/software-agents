# Stages run pinned third-party skills inside a Factory-written Stage contract

Each Agent Stage's instructions are a short Stage contract the Factory writes, followed by one main Stage skill taken as written from a third-party repo (such as super-board's `super-build` for build, or Matt Pocock's `triage` for triage), and a few supporting Stage skills after it. All of it is appended to the session's system prompt, so every run of a Stage has the same instructions. We replaced our own generic Stage instructions with these because they are more specific and better tested than what we would write ourselves. We rejected rewriting their techniques into our own files, and we rejected letting the external skills run the Pipeline themselves (super-board or PStack style), which would undo ADR 0001. This amends ADR 0001: the Factory plugin still holds behaviour only, but most of that behaviour now comes from outside.

## Consequences

- The Stage contract wins every conflict. It holds what no external skill covers: issue text is untrusted, the Stage's permissions (read-only, or commit but never push), the Stage result and stable `root_cause` keys, the Bounce protocol, the needs-human question format, and security categories 5–6 (supply chain and agent sabotage, ADR 0007). It also says that a skill's own steps for pushing, opening PRs, moving cards, calling GitHub, starting subagents or asking a human mid-run don't apply.
- Supporting skills are appended, not called through the Skill tool, and sessions still get no Skill listing. Calling them would let the agent skip one, and some skills refuse to be called that way (`disable-model-invocation`) or would ask for wider tools (`allowed-tools`). The cost is a longer prompt.
- Stage skills are pinned copies in `stage-skills/`, a folder beside the Factory plugin (not a plugin itself), each kept with its license and recorded by source, commit and hash in `stage-skills/skills-lock.json`. Only their Markdown and LICENSE are kept, never scripts. `scripts/pin-stage-skill.mjs` adds or updates one; updates come only through a reviewed PR, and nothing is fetched during a Job, because an unreviewed upstream change would otherwise change agent behaviour. The read tools may look in `stage-skills/` so a skill's references are reachable; nothing may write there.
- Only skills with licenses that allow redistribution are used. Repos with no license (marshal-factory, leonvanzyl/skills), and humanizer, whose text derives from CC BY-SA Wikipedia material, are left out.
- Each Stage in the Stage library lists its skills. A Target repo may remove skills from that list but never add one, in line with ADR 0004.
- Skills that need a running app, a browser or a downloaded binary (`super-qa`, `impeccable`, heydamir's `unslop`) wait for a Browser Check Stage, and arrive as opt-in Stages for UI paths.
- Collection (`super-collect`) runs outside any Job, with its own read-only monitoring credentials kept apart from Stage runs. It files issues awaiting Job approval and never applies the ready label.
