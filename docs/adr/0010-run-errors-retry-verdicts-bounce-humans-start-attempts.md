# Run errors are retried, fail Verdicts Bounce, and only a human starts a new Attempt

Every failure falls into one of five kinds, each with one fixed response. **Transient** errors (API overload or 5xx, network blips, GitHub 5xx or 429) are retried with backoff, three times over about five minutes, without counting. A **fail Verdict** (`stage-failed`) Bounces, as before. A **Run error** (`stage-errored`, `data.reason` one of `crash`, `sdk-error`, `invalid-result`, `timeout`, `budget`) is retried and counted. **Needs judgement** (Bounce cap or repeated root cause, three Guard denials, a failed Pre-push check, an issue changed since approval, retries run out) goes to a Human request. A **Factory fault** (Job store unwritable, bad credentials, App uninstalled, Sandbox unavailable) pauses or stops the whole Factory. We rejected treating every failure alike and retrying until a cap: it spends money repeating an expensive or deterministic failure, and it lets the Factory loop on its own. So a hard Budget hit is never retried, a repeated failure goes to a human early, and the Orchestrator never starts a new Attempt by itself.

## Consequences

- A Stage gets up to 2 retries per Attempt, resumes included. `crash` / `sdk-error` resume the session once, then start fresh; `invalid-result` resumes with the schema errors as a correction turn; `timeout` starts fresh; `budget` is never retried: the Job goes to paused (budget) with the cost and turns so far, and you raise the limit, retry or cancel (reconciled while implementing Policies, #25). A retry that hits the same reason in the same place (same failing command or schema error) skips the remaining retries. Retries run out → waiting, with `/approve` for one more try or `/cancel`; never a silent failure.
- Stuck detection: the wall-clock Budget (default 30 minutes) or 10 minutes with no SDK message aborts the session as `timeout`. Waiting, paused and queued Jobs are never stuck; a Job queued over a day only warns in `factory status`.
- Restart: a lock file allows one Orchestrator. At startup it replays the Event log, marks unfinished Stage runs `stage-interrupted` (then resume once or rerun), leaves plan-limit-parked runs until `resetsAt`, and deletes Working copies of no live Job.
- Ending a Job: cancelled closes the PR with a comment, deletes every Attempt's branch and the Working copy, removes the ready label and sets `factory:cancelled`; failed turns the PR into a draft, keeps branches and the Working copy for 7 days, and says how to retry (re-label or `factory retry`); merged deletes branches and the Working copy.
- Housekeeping sweeps at startup and hourly (7-day Working copies, 30-day Transcripts and artifacts except merged Evidence, orphans, failed branch deletions) and records one `housekeeping-ran` event.
- If the Job store can't be written, the Orchestrator stops. If GitHub is down, Stage runs carry on and merges wait. A refusal waiting won't fix (a 403 that isn't a rate limit, a 404 for a repo the App can't see) is a Factory fault instead: the Factory pauses (`github-refused`), naming the call and the permission GitHub asked for, the Job says so, and a restart once it's fixed lifts the pause (clarified while implementing #56). A config change that fails `factory config check` is rejected and the old config stays.
- Adds `stage-errored` and `housekeeping-ran` to the event types of ADR 0009.
- What an ending changes on GitHub (closing or drafting the PR, taking the ready label off, reopening a reverted issue) the Orchestrator writes itself, as ADR 0001 has it; the Mirror only posts why. Each write done is recorded as its own event (`pr-closed`, `pr-drafted`, `ready-label-removed`, `issue-reopened`), so while GitHub is down the missing ones are owed and tried again each pass, and none is made twice. One GitHub refuses outright is recorded with why and not tried again. Branches are deleted from the Trusted clone at the ending, and any deletion that fails is left to housekeeping (clarified while implementing PRs and merging, #33).
- The post-merge watch only follows the Factory's own merges, and looks at the first CI run after the merge: the merge commit's checks. The revert is made in the Trusted clone on a branch the Factory names (`factory/<issue>-revert-<pr>`), so a restart finds it again instead of reverting twice. Its PR is merged by the Factory in auto, only at the commit the Factory pushed, and left open for you in off and trial. Either way the Orchestrator reopens the issue and takes the ready label off, and the Mirror says why, so re-applying the label starts the next Job.
- A Target repo's `merge_method` (squash, merge or rebase; default squash) is how the Factory merges its PRs and reverts.
- A Job fails only when a human says so: a `/cancel` answering a request where the Factory gave up on its own (Bounce cap, repeated root cause, retries run out, Guard denials, a failed Pre-push check, nowhere to Bounce) ends the Job as failed, so its draft PR, branches and Working copy are kept 7 days to look at. Any other `/cancel` cancels it. The request says which one its `/cancel` does (decided while implementing PRs and merging, #33).
